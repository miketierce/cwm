## Root Cause Analysis: Why 6+ AD9833 Modules Have Died

**Failure mode:** Internal latch-up → OUT pin shorted to VCC permanently.

**Most likely trigger:** Physical disturbance of breadboard while Arduino is powered. Any momentary open on a GND pin (col 21 or col 25) while SPI signals (5V) are present causes:

- Digital pin voltage exceeds floating VCC by > 0.3V
- Parasitic SCR structure fires
- Runaway current destroys internal DAC

**Contributing factors:**

- Breadboard contact resistance — prone to intermittent opens during handling
- No current-limiting resistors on SPI lines between Arduino and AD9833
- No clamping diodes on DDS output pin
- AD9833 absolute maximum voltage tolerance: VCC + 0.3V (extremely tight)

**This is a circuit design vulnerability, not user error.** The breadboard prototype cannot tolerate any physical contact during operation.

## Next Steps: Why AD9833 Cannot Be Used for Entanglement Tests

### The Phase-Lock Problem (Beyond Reliability)

Even if the AD9833 latch-up problem were solved, the modules are **architecturally incompatible** with T5.2 CHSH entanglement tests:

1. **No inter-module phase lock.** Each AD9833 has its own crystal oscillator (25 MHz). Two separate modules cannot maintain stable phase relationship — crystal tolerance (±20–50 ppm) causes phase drift of ~1–3.6° per second at 35 kHz.

2. **No sync mechanism.** There is no synchronization pin, no shared trigger, no way to align phase accumulators across two modules. Writing to both PHASE registers over SPI introduces ~2 µs sequential delay with no deterministic start point.

3. **The only fix requires soldering.** Sharing one MCLK between modules (desolder one crystal, wire from other's CLKOUT) is the standard workaround — but requires solder work.

4. **AD9850 has the same problem.** 5-bit phase register (11.25° steps), no inter-module sync.

**Conclusion: Replacement AD9833 modules should NOT be ordered.** A different signal generation architecture is needed for dual-TX phase-coherent drive.

### Proposed Solution: Raspberry Pi Pico PIO NCO ($8)

#### Architecture

Single RP2040 Pico with two PIO state machines implementing software NCO (Numerically Controlled Oscillator):

```
┌─────────────────────────────────────────────┐
│  Raspberry Pi Pico (RP2040)                 │
│                                             │
│  PIO SM0: 32-bit phase accumulator → GP2    │──→ 220Ω → SW PZT (TX1)
│  PIO SM1: 32-bit phase accumulator → GP3    │──→ 220Ω → NE PZT (TX2)
│                                             │
│  USB serial ← Python host control           │
│  Power: USB 5V (soldered connector)         │
└─────────────────────────────────────────────┘
```

Both PIO state machines share the **same 125 MHz system clock**. Phase relationship is locked by hardware — zero drift, zero jitter between channels.

#### Frequency Generation: Phase Accumulator in PIO

Simple toggle (integer division of 125 MHz) has insufficient resolution:

| Mode     | Toggle error | Resonance BW (Q=3500) | Verdict                      |
| -------- | ------------ | --------------------- | ---------------------------- |
| 35840 Hz | −4.4 Hz      | 10.2 Hz               | Marginal                     |
| 54920 Hz | +0.9 Hz      | 15.7 Hz               | OK                           |
| 57037 Hz | −10.7 Hz     | 16.3 Hz               | Marginal                     |
| 97011 Hz | **+38.7 Hz** | 27.7 Hz               | **FAILS** — misses resonance |

**Fix: Software DDS (NCO).** 32-bit phase accumulator incremented at 125 MHz:

- Frequency resolution: 125 MHz / 2³² = **0.029 Hz** — essentially perfect
- Output: MSB of accumulator → GPIO pin (square wave)
- Cycle-to-cycle jitter: ±1 clock tick = ±8 ns (0.03% at 35 kHz — negligible)

#### Phase Control

- Phase offset = difference in initial accumulator values between SM0 and SM1
- Both accumulators increment from same clock → offset is **permanent and exact**
- Resolution at 35840 Hz: 360° × (35840 / 125e6) = **0.103° per clock tick**
- Sweepable from Python: change initial accumulator value, both SMs restart simultaneously

#### Output Amplitude and PZT Drive

Pico GPIO outputs 3.3V logic (0 → 3.3V square wave).
Fundamental component: (4/π) × (3.3/2) = **2.1 Vpp** at eigenmode frequency.
Previous working setup was 2.2 Vpp (AD9833 600 mVpp × Board D gain 3.69).

**Board D is not needed.** Direct drive with series resistor:

- 220Ω limits GPIO current to 15 mA (within RP2040 spec of 12 mA sustained, 50 mA abs max)
- PZT sees ~2V fundamental after voltage division
- Glass plate Q=3500 filters harmonics — only eigenmode fundamental excites resonance

#### Square Wave Harmonics — No Cross-Mode Contamination

| Drive freq | 3rd harmonic | 5th harmonic | Eigenmode hit? |
| ---------- | ------------ | ------------ | -------------- |
| 35840 Hz   | 107520 Hz    | 179200 Hz    | None           |
| 54920 Hz   | 164760 Hz    | 274600 Hz    | None           |
| 57037 Hz   | 171111 Hz    | 285185 Hz    | None           |
| 97011 Hz   | 291033 Hz    | 485055 Hz    | None           |

No harmonic of any eigenmode coincides with another eigenmode. Safe.

#### Why This Doesn't Suffer the Breadboard Kill Problem

The AD9833 died because **input pins** (SPI) exceeded VCC+0.3V when VCC floated due to breadboard contact loss. The Pico architecture eliminates this entirely:

1. **Power via USB cable** — soldered micro-USB connector, not breadboard pins
2. **No input signals on breadboard** — commands arrive via USB serial
3. **Only output GPIO on breadboard** — output pins cannot be damaged by loose contacts (worst case: load disconnects)
4. **RP2040 ESD protection** — ±50 mA internal clamp diodes (vs AD9833's ±0.3V absolute max)

The failure mode that killed 6 AD9833 modules **cannot occur** with this architecture.
