## Key Insights Discovered

### 1. Spectral Port Multiplexing — stacking plates per relay channel

**The reframe:** A relay channel is a "spectral port," not a "plate selector." You don't need to know which plate produced a resonance — only that "at frequency F, port C responds with amplitude A." The Q-factor provides 40–60 dB of intra-port isolation spectrally. The relay only isolates between ports; physics isolates within ports.

**Capacity math (corrected):**

- Usable bandwidth: 120 kHz (30–150 kHz)
- Mode width at Q ≈ 200: ~500 Hz
- Available spectral slots per port: ~240
- Real cap: ~48 plates/port (spectral saturation), NOT 3–4 as initially estimated
- At 8 plates/port: 92% efficiency (~37 usable modes)

**Impact:** Both HD (Level 2) and kernel (Level 3) paths benefit equally from stacking.

### 2. Multi-tone + FFT readout eliminates relay switching during gameplay

Drive ALL usable mode frequencies simultaneously as a multi-tone burst → capture ONE FFT → extract amplitude at each frequency bin → k features from one capture. No relay switching required during operation.

**Frame rate revolution:**

- Old (relay-scanned): 24 switches × 15 ms = 360 ms → 3 fps
- New (direct-wire, multi-tone): 1 capture × 15 ms → **66 fps**

### 3. Direct-wire is optimal for gameplay

If you never switch during gameplay, the relay contacts are just noise sources. Remove them from the signal path entirely:

```
All RX PZTs (parallel) → preamp → PicoScope chA → FFT → done
```

Relays retained ONLY for initial census (characterize plates individually, one-time).

**Benefits:** lower noise floor, no switching transients, simpler wiring, faster.

### 4. Pong at 66 fps on existing hardware ($0)

The Pong demo ("you're playing against glass") is now achievable at real-time frame rates:

- 8 plates, direct-wire to chA
- Multi-tone drive → single FFT → 37-dim kernel → ridge regression → paddle_y
- 15 ms decision time, 66 fps
- Training: 256 captures × 15 ms = 4 seconds total data collection
- Total build: ~2 sessions

### 5. DOOM at 66 fps on existing hardware ($0)

The same direct-wire approach means the DOOM first-person maze (originally specced at $68 + 32-plate FDM build) is achievable on the existing 8-plate cassette:

- 8 plates, 1 port, 37-dim kernel (exceeds the 32-dim requirement)
- 66 fps (originally required FDM for 125 fps — 66 is sufficient)
- Zero relay switching during gameplay

The 32-plate FDM path becomes the luxury upgrade, not the prerequisite.

### 6. Kernel dimension formula (corrected)

```
kernel_dim = usable_modes_per_port × N_ports
```

NOT simply "number of plates." The multi-tone FFT readout means each mode IS a kernel dimension. 8 plates with 37 usable modes on one direct-wire port gives a 37-dim kernel — higher than the original 32-plate spec.

## Pinned Idea: Proof of Physical Inference (blockchain)

**Concept:** A consensus mechanism where "work" = physically-unclonable kernel inference.

1. Register device kernel signature on-chain (PUF enrollment → device identity)
2. Network broadcasts query vectors
3. Glass evaluates its unique kernel (physically unclonable — can't be faked by GPU)
4. Submit 37-dim gradient response + PUF signature
5. Network verifies response is consistent with registered device kernel
6. Earn tokens for provably-physical inference

**Why it's defensible:**

- No GPU can fake a specific CWM kernel response (PUF property)
- The glass IS the identity AND the computer — same device
- Every response is signed by physics, not by a key that can be copied
- Unlike PoW, the "work" produces USEFUL inference (not wasted heat)

**Why existing blockchains don't fit:**

- SHA-256, ECC, ZK proofs all need bit-exact arithmetic
- Glass CAN do XOR/AND/NOT (§7A LUT cascade), but at 1-bit × 15 ms per op → 10²¹× slower than ASICs
- The competitive advantage is in approximate inference + physical unclonability, not exact arithmetic

**Status:** Concept only. Needs: (a) define the inference tasks the network would pay for, (b) design the PUF challenge-response that proves physical execution, (c) estimate revenue per device at desk scale vs MEMS scale. **Explore after Pong demo validates the kernel path.**

## Pinned Concept: Selection-Not-Writing Architecture (the "poker game" analogy)

**Documented verbatim so future references stay on the same page.** This came up when discussing whether "writing a result into a plate's spectrum" means physically altering the plate.

**User's framing (verbatim, 2026-06-20):**

> "do you mean that physically or with a virtual mask like we've used before? avoiding any kind of need for a 'piano hammer' or mechanical process to alter the plates. Instead the array is more like a deck of cards and if you think of it like a poker game — if our computation is showing a straight we know that we need [to] access the cards that build a flush."

**The agreed interpretation — selection, not writing:**

Nothing is ever stamped, modified, or mechanically altered. Every plate **already is** its data: its eigenmode spectrum was "written" once, permanently, when it was manufactured/cut/mounted. The array is a **pre-existing library of spectral identities** — a deck where every card already has its face value.

The computation is **not**:

> ~~compute → write result into plate Y → later read Y back~~

It **is**:

> compute on plates X → the result tells you **which** plate(s) in the array to address next → read that plate's pre-existing spectrum → **that spectrum IS your answer**

```
  Computation (your hand)            The array (the deck — all faces fixed)
  ┌──────────────────────┐          ┌──────────────────────┐
  │ Interfere modes on   │          │ Plate Y₁ = spectrum α │
  │ plates X₁, X₂, X₃    │──result─▶│ Plate Y₂ = spectrum β │
  │                      │  ("need  │ Plate Y₃ = spectrum γ │ ◀ address this one
  │ "I'm showing a       │  a flush │ Plate Y₄ = spectrum δ │
  │  straight"           │  → γ")   └──────────────────────┘
  └──────────────────────┘
```

The crossbar performs **memory recall by routing** — not by retrieving something that was written, but by addressing the plate that already embodies the answer. The "piano hammer" (any mechanical write mechanism) is eliminated entirely.

**Poker mapping for quick reference:**

| Poker term          | CWM meaning                                                        |
| ------------------- | ------------------------------------------------------------------ |
| The deck            | The full plate array (all spectra fixed at manufacture)            |
| A card's face       | One plate's eigenmode spectrum (its permanent identity)            |
| Your hand           | The current interference computation on the input plates           |
| "I have a straight" | The computed result / partial state                                |
| "I need a flush"    | Which target plate(s) to address next                              |
| Playing the card    | Crossbar routes to that plate; reading it returns the stored value |

**Status:** Architectural framing, agreed. Distinct from the rewrite/re-encoding path — this is the **read-only selection** model. Relevant to the kernel/associative-memory path, not the writable-state path.

## Critical Findings (Encoding Architecture)

### Single-tone encoding FAILS

The initial approach mapped 256 game states onto a 1D frequency line (35–140 kHz). Result: 29% intercept = equal to stationary paddle. Fisher discriminant ratio = 0.152. The kernel response lives on a 1D manifold — states are inseparable regardless of how many readout modes you use.

**Lesson:** Encoding dimensionality must match or exceed the number of independent state variables. One tone for a 2D+ state is information-theoretically doomed.

### Census modes are noise for readout

Driving at frequency f does NOT reliably excite modes at other frequencies on separate plates. Mode-amplitude SNR ≈ 0.6 (below noise floor). The original plan to "read 30 census modes as features" produces pure noise.

### Drive-frequency response IS the signal

Reading a **window of FFT bins around each drive tone** captures the glass transfer function at that frequency. This is where the glass actually does useful computation:

- Drive-window SNR = 5.28
- Correlation with ball_y = 0.64
- Test-retest reliability r = 0.84

The glass shapes the spectral response around the drive frequency depending on the mechanical state. This is the kernel evaluation.

### Glass TRACKS, does not PREDICT

| Target         | Intercept | R²    | vs Stationary | vs Random      |
| -------------- | --------- | ----- | ------------- | -------------- |
| Track ball_y   | **59%**   | 0.29  | +9% (beats)   | +23% (beats)   |
| Predict bounce | 47%       | −0.14 | −9% (loses)   | +9% (marginal) |

Tracking is smooth and learnable. Prediction requires modelling wall bounces — chaotic dynamics the glass can't resolve at current kernel dimension.

### Intermod across separate plates is weak

Cross-plate intermodulation SNR ≈ 1.0. Real nonlinear mixing requires driving multiple tones on the **same** plate. Software quadratic cross-products serve as the readout nonlinearity instead (clearly labelled).

## Retrain Results — F2 vs F5 Comparison (00:05–00:07)

Ran two training passes back-to-back to test which channel should carry the `ball_y` tracking target. Both used 256 states, navg=24, target=track, ~116 s data collection each.

| Run | ball_y channel | Usable modes       | Best intercept  | vs Stationary | Verdict               |
| --- | -------------- | ------------------ | --------------- | ------------- | --------------------- |

| 2   | F5             | 10 (SNR 3–7)       | 43% (α=1.0)     | −7 pts        | ❌ no advantage       |

**Baselines:** random 36%, stationary 50%.

### The hypothesis was WRONG — and the result is instructive

I predicted F5 (10 modes) would beat F2 (1 mode) because it adds kernel dimension. **The opposite happened.** F2 won decisively (68% vs 43%).

**Why a single strong mode beats ten weak ones for 1D tracking:**

The `ball_y` target is encoded as a frequency sweep across 70–100 kHz. For the glass to track it, the drive sweep must traverse a resonance whose response varies **monotonically and cleanly** with frequency.

- **F2** has exactly one mode in that band — at 85 kHz, SNR 13 (the strongest resonance in the entire census). As ball_y sweeps 70→100 kHz, the drive passes through this single sharp peak, producing a clean, high-SNR, well-ordered response. Perfect for a 1D readout.
- **F5** has four modes in the band (74.5, 80.5, 91, 98 kHz), each SNR 3–4. The sweep hits multiple weak overlapping resonances → a jagged, non-monotonic transfer function. More features, but they encode the position ambiguously and noisily.

**Lesson (recorded to memory):** For a 1D tracking variable encoded as a frequency sweep, **one clean high-SNR mode the sweep traverses beats many scattered weak modes.** Kernel dimension helps multi-dimensional classification, but for a single continuous readout, SNR and monotonicity dominate. The "more plates = better" rule does not apply to per-axis tracking.

**This is also the best Pong result to date — 68% vs the prior session's 59%.** The improvement came from F2's clean mode (and possibly the RX wiring changes raising its SNR), not from the 5th plate.

## Collision Modes Are NOT Useless — They Carry Signal (01:12)

**Prompted by the question "why do we throw collision modes away?"** — the same reframe that turned "census modes are noise" into the drive-window signal, and "F3 dead" into F3 alive. Investigated whether the collision filter discards real compute.

### First, the smoking gun: the filter has an inverse-quality bias

The collision filter drops any mode sharing a bin (within 500 Hz) with another channel's mode. On the corrected 40-mode census:

| Pile                   | n   | mean SNR | modes ≥6× |
| ---------------------- | --- | -------- | --------- |
| Kept (usable)          | 40  | 4.4      | 5         |
| **Tossed (collision)** | 120 | **4.8**  | **22**    |

**11 of the 12 strongest modes in the entire census were discarded** — including the single strongest resonance (55 kHz, SNR 13). Strong modes are strong because they're low-order plate fundamentals, and similar plates share those frequencies — so the filter systematically selects _against_ the best modes.

### The conceptual error

"Collision" measures **spectral ambiguity** (which plate owns the bin), not **usefulness**. A collision bin holds the _coherent interference sum_ of two plates — a state-dependent, repeatable quantity. For a **learned** readout (ridge regression), attributability is irrelevant; what matters is whether a feature is **repeatable** and **correlates with the target**. Discarding by attributability is the wrong filter.

### The test (real glass, [tools/collision_value_test.py](tools/collision_value_test.py))

One data collection (256 ball states, 3 encoding tones, navg=16), then leakage-free top-K feature selection (rank by train-fold correlation, evaluate on held-out fold) on the proven track-ball_y task:

| Feature pool (K=20 selected)       | Intercept                       | Collision modes picked |
| ---------------------------------- | ------------------------------- | ---------------------- |
| Non-collision only (40 candidates) | 50% (= stationary)              | 0                      |
| **All modes (160 candidates)**     | **65%** (+15, beats stationary) | **16 of 20**           |
| drive-window readout (same run)    | 51%                             | —                      |

**Per-mode |correlation with ball_y|:** non-collision mean **0.065**, collision mean **0.061** — statistically identical.

**Data:** `data/results/collision_value/collision_value_20260621_011239.json`

### Verdict

1. **Collision modes carry as much target signal as non-collision modes** (0.061 vs 0.065 mean corr). The "collision" label is **orthogonal to usefulness.**
2. **Including them improved tracking 50% → 65%** in the same run, and the selector preferred them 16-to-4. Discarding 120 of 160 modes was throwing away real, generalizing features.
3. **Honest nuance:** dumping all 160 raw into ridge overfits (36% at 256 samples). The value is harvested by **selecting/regularizing from the full candidate pool**, not by blindly keeping everything. Rule: keep all modes as candidates; let selection decide. "More features" is not automatically better — "more _candidates_ to select from" is.

### What changed

- [tools/direct_wire_census.py](tools/direct_wire_census.py): added `--keep-collisions` (tag instead of discard) and `--repeat-passes N` (score each mode by test-retest repeatability — the principled replacement for the attributability filter). Modes now carry `collision` and `repeatability` fields.
- [tools/collision_value_test.py](tools/collision_value_test.py): new decisive value test (built + validated dry-run + run on hardware).
- WL-B10 kill criterion softened: low collision-efficiency is a proxy, not the goal; rank by repeatability × |corr|, not by attributability.

### Overfitting — what it is, and the knobs (demonstrated on our data)

"Dumping all 160 into ridge overfits" = **the weight vector overfit** — 160 coefficients fit to 256 samples bend to fit training-fold noise. The in-sample-vs-held-out _gap_ is the overfitting. Measured on our data:

| Knob                            | Effect                                                                       |
| ------------------------------- | ---------------------------------------------------------------------------- |
| Regularization (α): 0.01 → 1000 | gap 45 → 5 pts, but plateaus at 42% (can't separate 5 signal from 155 noise) |
| Fewer features (top-K): 20      | **65%** — removing noise beats down-weighting it                             |
| More data                       | the untouched knob — 160 features overfit far less with >256 samples         |

α and feature-count are the same complexity knob; the winner is **select from the full pool, then regularize the survivors.**

### DOOM render — NEGATIVE RESULT (and it's diagnostic)

Trained DOOM on real glass (216 states, navg=16, full mode pool). **Direct rendering failed:** best RMSE 0.364 is _worse_ than the mean-profile baseline (0.325); silhouette r ≈ 0.00.

A leakage-free diagnostic on the same data shows exactly why:

| Target                                    | CV R²                       |
| ----------------------------------------- | --------------------------- |
| Player **angle** (smooth)                 | **+0.48**                   |
| Player **y** (smooth)                     | **+0.36**                   |
| Player x (smooth, weak F1 band)           | +0.09                       |
| The 8 **raycast columns** (discontinuous) | **≈ 0.00** (−0.07 to +0.08) |

**The glass reads back the smooth state variables but cannot produce the raycast columns.** Raycasting wall distances is a _discontinuous_ function of (x, y, angle) — a ray abruptly hits or misses a wall — and a smooth analog kernel + linear readout cannot represent a discontinuity. This is the **predict-vs-track lesson, generalized**: the glass tracks (smooth) but cannot predict bounces / raytrace walls (discontinuous).

**Correction to an earlier claim:** I previously wrote "40 modes ≥ 32 → scrappy DOOM runs on current hardware." **That was wrong.** Kernel dimension is _necessary but not sufficient_; the render function must also be smooth enough for the kernel to represent. Raycasting isn't. DOOM needs the **associative-recall architecture** (one plate per stored view → recall nearest precomputed view, the §7A discrete/LUT path), which is the 32-plate build — not a current-bench demo. Launching the trained DOOM model as if it worked would have been exactly the kind of board-cheating we've been avoiding; it is recorded as a clean negative.

**Value of the negative:** it sharpens the architecture boundary — the glass is a smooth kernel (§7B gradient path), not a discontinuous-geometry engine (§7A lookup path). Pong tracking sits on the right side of that line; raycasting sits on the wrong side. The build ([tools/doom_train.py](tools/doom_train.py), [tools/doom_live.py](tools/doom_live.py)) is kept — it's the correct harness for the future 32-plate associative-recall version.

## DOOM Reframe — Three Angles Tested, the Real Limit Found (01:58)

The negative DOOM result isn't a dead end — it's a prompt to stop forcing the **silicon algorithm** onto a **wave computer**. Tested three reframes on the _existing_ glass capture (no new hardware), each leaning further into glass-native strengths.

### Angle 1 — Volumetric (fog) render instead of hard raycast ✅ direction confirmed

Hard raycasting is discontinuous _because of the first-hit branch_ — pure silicon thinking. The wave-native render is **volumetric**: integrate soft wall-occupancy along each ray (the volume-rendering integral — the same reason NeRF uses it instead of hard ray–surface intersection, to stay learnable by a smooth approximator). Same glass capture, only the target changed:

| Render target          | mean per-column CV R² | smoothness (Δ across adjacent angle) |
| ---------------------- | --------------------- | ------------------------------------ |
| Hard raycast (silicon) | **−0.00**             | 0.622                                |
| Soft volumetric (wave) | **+0.30**             | 0.075 (8× smoother)                  |

Every column went from noise (R²≈0) to a consistent +0.28–0.32, and a full retrain on soft targets now **beats** the mean-profile baseline (RMSE 0.288 vs 0.339) where hard raycasting was _worse_ than baseline. **The reframe direction is correct: render smooth fields, not hard edges.**

### Angle 2 — Associative recall (the §7A path) ❌ blocked by state resolution

Tried the architecturally-blessed DOOM: glass identifies your state, a table holds the crisp precomputed view. Leave-one-out nearest-neighbor in glass-feature space:

- recalled neighbor in the **same cell: only 15%** (≤1 cell: 30%)
- recalled neighbor **same facing: 37%** (≤1 step: 51%)
- recalled-view RMSE 0.817 vs baseline 0.580 — **worse** than the mean.

The glass features don't cluster sharply enough by state to recall 1-of-216. Recall fails not because the idea is wrong but because **state discrimination is too coarse** at this scale.

### The real limit — STATE RESOLUTION, not render form

Both angles converge on the same diagnosis. The glass reads back **coarse smooth state** (angle R²=0.48, y R²=0.36, x R²=0.09) but cannot pin down 1 of **216** distinct states. This matches the long-standing resolution finding (effective ~1–2 levels per axis). DOOM-8×8×8 simply asks for more state resolution than 5 channels provide — independent of whether the render is smooth or recalled.

### The synthesis (leaning into the strength, not the silicon mold)

The glass is a **smooth, low-dimensional kernel.** Its wins are exactly there: Pong 1-D tracking (r=0.69, won 41–18) and reading facing-angle (R²=0.48). Its losses are where silicon excels: discontinuous branching (raycast, bounce-predict) and high-state-count discrimination (216-state maze).

**The glass-native game is low-dimensional and smooth — not a 216-state maze.** Three honest forward paths, in order of fit:

1. **Embrace the fog: "glass sonar/proximity" render.** Present the soft volumetric render for what it is — the glass _sensing_ walls as a smooth proximity field (walls glow brighter as you near them). Honest, demoable, leans into the smooth strength. Not a crisp raytracer, and we don't call it one.
2. **Reduced-state maze** (e.g. 4×4 × 4 dirs = 64 states) so each state is distinct enough for crisp render or recall. Needs one new hardware capture.
3. **A 1–2-D smooth-control game** (steering/racing: track-position → steering correction) — Pong's proven winning mechanic in a new skin. Highest-confidence win.

**No board-cheating:** we do **not** claim DOOM renders on the current bench. We claim we mapped exactly why, and found the axis (low-dim + smooth) where the glass genuinely computes.

## Associative Recall Done Right — Diary Review + The Diagonal Matrix (02:00–02:20)

Reviewed every lab diary for **proven** readouts (subagent sweep). The result reframes the DOOM failure entirely: **we'd been using the silicon tool (ridge regression on frequency-encoded state) when the glass's proven strength is associative recall (nearest-centroid on amplitude-encoded modes).**

### What the proven 100% results actually did

| Experiment                    | Result                 | Method (the part we'd been ignoring)                                                               |
| ----------------------------- | ---------------------- | -------------------------------------------------------------------------------------------------- |
| T1.3 eigenmode discrimination | 100%, **193σ**         | sequential per-mode drive, read mode's own bin, "perfect diagonal confusion matrix"                |
| T3.4 multi-level              | **4096 states, 100%**  | **amplitude** of fixed mode (8 levels), nearest-centroid/Mahalanobis. **Ridge FAILED here: 0.55%** |
| T3.3 reservoir                | 100% (4-class)         | per-mode amplitude, ridge ok for _few_ classes                                                     |
| Rod associative recall        | 100% (4/4, 7 sessions) | template match = nearest-neighbour                                                                 |

**Two things leap out:** (1) the proven high-resolution encoding is **amplitude of a fixed mode**, not **frequency position**; (2) the proven classifier is **nearest-centroid**, and **ridge regression explicitly failed** at high class count (T3.4: 0.55%) — the exact tool we used for DOOM.

### The diagonal matrix (the user's intuition, confirmed)

The desk protocol defines CAM success as the **Gram matrix K_ij diagonal-dominant** (each state most similar to itself). Built it from the DOOM capture ([tools/cam_analysis.py](tools/cam_analysis.py)):

- All features / noisy features → off-diagonal ≈ 0 (no structure to exploit).
- **Top-10 separability-selected modes → off-diagonal 0.048** (diagonal structure appears).

So "if we aren't using census data correctly the diagonal is hard to spot" is literally true: **selecting modes by separability is what makes the Gram matrix diagonal.**

### Factored recall is alive (it was the framing that was dead)

Instead of ridge-regressing the render or 1-of-216 nearest-neighbour (15%, looked hopeless), use **factored nearest-centroid** — resolve each axis independently (the T3.4 trick):

| Axis  | nearest-centroid acc (all feat → top-sep) | chance |
| ----- | ----------------------------------------- | ------ |
| x     | 47% → 52%                                 | 17%    |
| y     | 56% → 60%                                 | 17%    |
| angle | 48% → 54%                                 | 12%    |

3–4× chance per axis. **The glass does know roughly where you are and which way you face** — the CAM path is alive; ridge + joint-216 was the wrong frame.

### The real ceiling — and the hardware/protocol tweak it points to

Ran the **proven method** on hardware ([tools/cam_recall.py](tools/cam_recall.py)): sequential per-axis drive + 6 repeats + Mahalanobis nearest-centroid. Per-axis accuracy was still only ~50–67% at 2 levels, **non-monotonic** (L=8 sometimes beat L=4) despite 5–6σ adjacent-level separation. That non-monotonic signature is the smoking gun:

**We encode state as a DRIVE FREQUENCY (where in the band). The glass transfer function is bumpy across frequency, so sweeping a state value jumps between resonances — non-monotonic, ~2 levels/axis.** The proven T3.4 method encoded state as the **AMPLITUDE of a fixed mode** — monotonic, 8 levels at 100σ.

**This is the wave-native correction, and it needs amplitude control.** The Pico NCO is a fixed-amplitude square-wave (frequency-only) source — structurally the wrong drive for the proven method. Amplitude encoding needs the PicoScope **AWG** (2 Vpp, settable) or the on-hand **MCP4921 DAC**. That is the single highest-value hardware/protocol tweak:

> **Encode each state axis as the amplitude of a fixed resonant mode (AWG/DAC drive), read that mode's bin, classify by nearest-centroid.** This is the literal replication of T3.4 (which hit 4096 states at 100%) applied to game state — the proven path to the resolution DOOM/recall needs.

## Amplitude Encoding Built + Validated — and Honestly Decomposed (09:00)

Acted on the finding. The AWG path was a dead end (tested: [tools/awg_amp_test.py](tools/awg_amp_test.py) — the PicoScope AWG is **not wired** to any TX PZT, all responses at noise floor). So amplitude control was added to the **NCO firmware via duty cycle** instead — no rewiring.

### Firmware: duty-cycle amplitude

New command `A<ch>:<permille>` (10–500 = 1–50% duty). A square wave's fundamental amplitude at the mode scales as **sin(π·duty)**, so duty is a clean amplitude knob on the fixed-voltage NCO. `apply_duty()` re-splits high/low preserving the period (frequency unchanged); harmonics move to 3f/5f and are rejected by the plate resonance. STATUS now reports `DUTY:d1..d5`. Flashed + validated ([tools/amp_validate.py](tools/amp_validate.py)):

| Channel         | amplitude range | monotonic?                                    |
| --------------- | --------------- | --------------------------------------------- |
| **F5 @ 89 kHz** | **8.1×**        | ✅ clean                                      |
| **F4 @ 48 kHz** | **5.0×**        | ✅ clean                                      |
| F1 @ 57 kHz     | 2.2×            | ✗ bumpy (duty harmonics hit other resonances) |
| F2 @ 82 kHz     | 3.1×            | ✗ bumpy                                       |

Two clean monotonic amplitude channels — enough for 2-axis encoding.

### Amplitude Pong: 100% CV — but it's CHANNEL RESOLUTION, not compute

[tools/pong_train_amp.py](tools/pong_train_amp.py): ball_y → F5@89kHz amplitude, ball_x → F4@48kHz amplitude, 64 states × 4 repeats, **leave-whole-state-out CV** (no identical-drive leakage). Result: **100% intercept** (vs 68% frequency-encoding, 50% stationary).

**Mandatory honesty decomposition** (decode ball_y from feature subsets):

| Feature subset                             | ball_y decode               |
| ------------------------------------------ | --------------------------- | --- | --------- |
| F5 ball_y-window only (the driven channel) | 99%                         |
| F4 ball_x-window only (different channel)  | 38% (clean separation ✅)   |
| census modes only (not the driven window)  | 99%                         |
| everything except F5 window                | 99%                         |
| `                                          | corr(F5 center bin, ball_y) | `   | **0.968** |

**Verdict: the 100% is real but it is a CHANNEL-RESOLUTION result, not a COMPUTE result.** We encode ball*y as amplitude at 89 kHz and read back amplitude at 89 kHz (and its harmonic footprint across modes). The glass faithfully \_carries* the amplitude through its high-Q resonance — the genuine T3.4 result (8 clean levels) — but the readout is substantially **loopback**, not the glass transforming anything. It is a _higher number_ than the 68% yet a _weaker compute claim_: the 68% had the glass transfer function doing nontrivial frequency shaping, whereas this reads back the level we set.

**What is genuinely won:**

1. The encoding finding is **confirmed on hardware** — amplitude-of-fixed-mode is a far cleaner channel (100% vs 68%) than frequency-position, exactly as the diary review predicted.
2. Clean 2-channel separation (ball_x does not leak into ball_y).
3. **The real prize:** this proves the glass resolves **~8 clean levels per axis** — precisely the resolution that was blocking DOOM / associative recall. The model metrics were annotated with this honest interpretation (not "compute").

### Decision

Do **not** ship the loopback 100% as "glass computes Pong" — that would be the board-cheating we've avoided all session. Instead, pivot the now-proven 8-level resolution into the **genuine** win: a reduced-state DOOM / associative-recall demo where amplitude-encoded axes give crisp state, recalled by nearest-centroid (the T3.4 method). That is compute-via-recall, not a wire.

## Pinned Concept: The Sum-Over-Histories / Path-Integral Framing (documented so we don't drift)

**User's intuition (2026-06-21):** "our deck approach is resolving states almost like reality itself … we are pattern matching every possible future state and the possible future states of those states and assigning probabilities."

This is a real structural correspondence to Feynman's path integral, worth stating precisely — with the honest line between the structure (real) and the mechanism (classical analog).

**Where the correspondence is literal (not metaphor):**

1. **Parallel evaluation over all states.** One broadcast query evaluates every enrolled card's resonance _simultaneously_ in one acoustic settling time. The defining move of the path integral is that the sum over histories is taken _all at once_, by the physics — not path-by-path.
2. **Interference selects the answer.** A content-addressable memory relaxes to the nearest stored attractor: energy accumulates at the match, cancels elsewhere. That is the path integral's "constructive interference near the stationary path, destructive cancellation everywhere else."
3. **Amplitude → probability.** The match-similarities across the deck _are_ a distribution (softmax / inverse-distance over stored states). "Assign probabilities over candidate futures weighted by match" is exactly what nearest-match over a complete deck computes. |amplitude|² → probability has the same shape.

**The honest caveats (classical analog, not quantum):**

- **Real energy, not complex phase.** The path integral's power is complex $e^{iS/\hbar}$ phase interference. We have real acoustic-energy interference → a _classical analog_ of sum-over-histories, not the quantum one. (The phase channel was killed as too noisy at bench; if revived, the analogy tightens.)
- **Sum over STORED histories, not generated ones.** Software enumerated each landing and we enrolled it. The glass does the parallel _matching_; it does not yet _generate_ the dynamics from a least-action principle.

**The buildable extension (the recursion the user named — "future states OF those states"):**

Single-step recall is a lookup. But if each card also stores _which cards are reachable next, with what amplitude_, then **iterating the recall walks a probability-weighted tree of futures** — a discrete path-integral / Markov sum over the deck, executed by the glass's parallel matching at each step. This is concrete and testable, not analogy.

**Modern anchor (makes the intuition current, not just historical):** transformer **attention is associative retrieval** — "Hopfield Networks is All You Need" (Ramsauer et al. 2020) proved attention = softmax recall over a stored set, a continuous Hopfield memory. So "pattern-match every state and assign probabilities" is simultaneously (a) the structure of Feynman's sum-over-histories, (b) the operating principle of Hopfield/CAM, and (c) the core of transformer attention. The deck is a _physical_ instance of the same primitive.

**Status:** Framing pinned. Use this language when the path-integral/Feynman analogy recurs. Keep the "classical analog (real energy), sum over stored histories" caveat attached — same honesty discipline as the CHSH "classical analog of quantum structure" rule.

## "ENERGY, NOT PHASE" — the honest difference, and a correction (2026-06-21)

User asked the right question: when I say we have _acoustic energy, not complex phase_, what is the honest difference — and was our earlier "phase failed" actually a **wave-native** test? Pulling the record, the honest answer is twofold.

### What "energy not phase" means in OUR pipeline

Our recall/CAM matches on the **magnitude spectrum** `|FFT(signal)|` — the energy at each mode bin — and computes Euclidean distance between magnitude fingerprints. We **discard the phase angle** of each complex bin. So our "interference" is really energy comparison: two cards are close if their mode energies are close.

A genuine path integral sums **complex amplitudes** $e^{iS/\hbar}$. The phase is the whole point: two paths of equal magnitude can **add** (constructive) or **cancel** (destructive) by their phase difference. Cancellation is what makes the sum compute — wrong paths destructively cancel, leaving the stationary (least-action) path.

The concrete difference, made sharp by the recursion experiment below:

|                         | our recall (magnitude)                        | true path integral (complex)    |
| ----------------------- | --------------------------------------------- | ------------------------------- |
| contributions           | real, **non-negative**                        | complex                         |
| combine by              | **adding** only                               | adding **or cancelling**        |
| math type               | classical probability / Markov sum / heat eq. | quantum amplitude / Schrödinger |
| can wrong paths cancel? | **no**                                        | yes                             |

So our sum-over-histories is the **classical analog**: a real, additive sum over _stored_ histories. Honest and correct as stated.

### The correction: "phase failed" was NOT a wave-native test

The "phase is too noisy" belief traces mostly to the **re-excitation interference test (T2.1, 2026-05-26)**, where the _sign_ of interference flipped randomly run-to-run. But the diary's own diagnosis says why: _"The PicoScope AWG restarts at fixed phase but the residual vibration phase depends on OS-level `time.sleep()` jitter"_ and _"the AWG cannot restart at a controlled phase relative to the decaying eigenmode."_ That is an **instrument + OS-scheduler artifact, not a property of the glass.** It was not wave-native — the phase _reference_ was broken by the AWG and the operating system, not by the physics.

Meanwhile, **two phase results actually succeeded**, and I had under-weighted them:

- **T3.2 Phase-Spectral Encoding (2026-05-26): PASS.** With triggered AC-coupled capture, per-mode phase was stable to **σ = 0.12–0.28 rad**, temporally stable (0.124 rad over 30 s, drift −0.04°/s). The only "no" was that the four modes' _mean phases_ overlap within 2σ — i.e. phase can't tell you _which mode_ (it was never meant to). As a second axis _within_ a mode it passed.
- **E9 Phase Cancellation (2026-06-03): PASS, decisively.** Two NCO channels at the **same frequency, 180° relative phase, from a shared 126 MHz clock** → mode energy cancelled by **98.9% ± 0.3%**, contrast 99.1%, fully reversible. **This is genuine wave-native phase interference — destructive cancellation on command.** It is exactly the "paths can cancel" ingredient the path integral needs, demonstrated at 99% on this bench.

### Synthesis — we conflated two different "phases"

1. **Absolute phase vs the lab clock / capture trigger** — this is what was noisy, and it was noisy because of the **AWG + OS timing** (not wave-native). Triggered AC capture already tames it (T3.2, 20× improvement over free-running).
2. **Relative phase between two coherent sources sharing one clock** — this is **deterministic and powerful** (E9, 99% cancellation). Our NCO has a `PHASE:` command and all PIO channels derive from the **same 126 MHz clock**, so relative phase **is controllable today.**

**Honest bottom line:** "energy not phase" accurately describes our _current recall math_ (we match magnitudes), but it is **NOT a proven limit of the glass.** We have hard evidence (E9) that coherent phase interference — including the destructive cancellation that is the quantum-like ingredient — works at 99% on this exact bench. We shelved phase for the wrong reason: a non-wave-native AWG/timing artifact. **Phase is an untapped wave-native channel, not a failed one.** → New worklist item: revive phase as a complex edge weight in recall (see recursion result + `EDGE_WEIGHT` hook).

### Root cause (first principles — this is the honest core)

Each tone's FFT phase is `intrinsic + 2π·f·t0`, where `t0` is the capture window's time offset relative to the NCO clock. In **free-run** (and in our "triggered" mode, which auto-fires), `t0` is **uniform over many tone periods** capture-to-capture. Critically, the phase **difference between two different frequencies** is `(intr_a − intr_b) + 2π(f_a − f_b)·t0` — it **still carries t0** unless `f_a = f_b`. So:

- **absolute** per-mode phase is uniform random across captures, and
- **cross-frequency** phase (the reference trick) also carries `t0` and **wraps** unrecoverably once `t0` spans more than one beat period.

The reference subtraction cancels `t0` only in the _unwrapped_ phases; over a uniform multi-period `t0`, the wrapping defeats both single-reference and dual-reference vernier. **Confirmed empirically and analytically.** There is no usable phase without a shared **drive↔capture time reference**.

Our compute bench drives with the **external RP2040 NCO**, asynchronous to the scope; the scope's threshold trigger on an async signal just auto-fires. ### CORRECTION — "tee the bus" was wrong for a multi-source NCO; use a SUMMING NETWORK (13:50)

User asked, correctly: _each GP pin has its 220Ω and lands on its own row shared only by the TX PZT and the jumper to the shared Ch B — how did you imagine I'd share the NCO output?_ My earlier instruction _"tee the whole drive bus → Ch B"_ was **wrong for this hardware, and I own it.** A "tee" splits **one** source two ways (the proven 320× note had a single AWG — nothing to short). With **five independent GP sources**, a single shared Ch B node doesn't tee them — it **shorts them to each other.**

**The short, quantified (matches the bench):** when GP2 drives F4 and the other four pins sit idle (`Foff` holds them low), the chained Ch B node ties all rows together, so the idle pins' four 220Ω resistors hang on GP2's row as a ~55Ω load to ground. GP2's row divides to `3.3V × 55/(220+55) ≈ 0.66 V` — **matching the measured ~500 mV**, confirming the rows are shorted (cross-driving every plate, and starving the drive = limiter #2).

**Corrected wiring — a SUMMING resistor in each jumper (Rs = 4.7 kΩ = "4K7"):**

```
GP2 ─220Ω─┬─ row ── TX2 PZT
          └─[4K7]─┐
GP3 ─220Ω─┬─ row ── TX3 PZT
          └─[4K7]─┼─→ Ch B   (the ONLY shared point, summed through resistors)
GP4 ─220Ω─┬─ row ── TX4 PZT
          └─[4K7]─┘            (… same for GP5/F5, GP6 etc.)
```

Because Rs = 4.7 kΩ ≫ 220 Ω drive R:

- **Rows isolated:** a tone reaches another row only through 2·Rs ≈ 9.4 kΩ → cross-coupling ~50% → ~1–2%.
- **Full drive restored:** each pin drives its PZT through 220 Ω essentially unloaded → row recovers ~3.3 V (≈2.4× more acoustic drive → directly fixes the weak Ch A SNR).
- **Ch B still sees every tone:** each drive reaches the common node through its own Rs → a clean summed copy (~0.36 V per tone) with all phases intact = exactly the reference `Za/Zb` needs.

**Resistor decode (user's kit had 4R7 / 47R / 4K7 — the labels are deceptively similar):**

| label   | value      | use?                                                                     |
| ------- | ---------- | ------------------------------------------------------------------------ |
| 4R7     | 4.7 Ω      | ✗ catastrophic (smaller than the 220 Ω drive R — hard short)             |
| 47R     | 47 Ω       | ✗ too small (≈ the ~55 Ω idle load that caused the bug; barely isolates) |
| **4K7** | **4.7 kΩ** | ✓ **USE THIS** — 21× the drive R; isolates rows, restores drive          |

Convention: the letter is the decimal point + multiplier — **R**=×1, **K**=×1000. So 4R7=4.7Ω, 47R=47Ω, **4K7=4.7kΩ**. **Use 4K7 in every jumper, between the row and the shared Ch B node.**

**Lesson (recorded):** one BNC tee for one source; a **summing network (series R per source)** for many sources. Never directly splice independent drivers onto a common node. **Rule of thumb:** summing R ≥ 10× the source/drive resistor (here 4.7 kΩ vs 220 Ω = 21×).

## Pinned Concept: PHASE-ENCODED HEADING — exact rotation as a card feature (user, 2026-06-21)

Full-circle heading needs **two independent readouts (I/Q quadrature)** — a second pair at a 90°-shifted reference, OR the **3-path rig**, whose two independent cross-terms (1↔2, 2↔3 phases) are precisely the two projections needed. So the user's "180° of freedom" is exactly right for the unambiguous half; the 3-path plate is the route to the full circle.

Prediction: continuous heading predicts _exact_ reflection angle where binary only flips a sign. **Status:** pinned; the natural next build after the validated binary in-motion deck. ## Pinned Concept: the IN-MOTION deck — cards are path-segments, not points (user, 2026-06-21)

**User's idea:** instead of a card per _arrived_ ball position, have a card for every _in-motion_ state — "like interlaced frames and motion blur on a paused TV." Every slice of the present then **contains a piece of the past**, which narrows the range of possible futures to rank. Poetically: we always exist in the _transition_ between two states, never actually "arriving."

**Why this is right, and deep (not just poetic):**

1. **It fixes the exact limitation I raised — "the glass sees only the present, not the past."** A static snapshot gives position but not velocity, so the future is maximally ambiguous (the ball could be heading anywhere). An _in-motion_ card embeds direction, collapsing the future cone to a narrow wedge. This is the honest answer to why single-instant recall under-determines prediction.

2. **It is delay embedding (Takens' theorem), which we already have a tool for.** [analysis/delay_embedding.py](analysis/delay_embedding.py) exists. Takens proves you can reconstruct a dynamical system's _full_ state — including velocity — from a time-delayed trace of a _single_ observable. A "motion-blurred" card is exactly a crude delay embedding: the blur **is** the velocity coordinate, recovered without a separate sensor. So the user re-derived Takens from the TV-pause intuition.

3. **The glass does the motion blur FOR FREE via its own ringdown (this is the key physical hook).** The plate has memory: Q≈3500 at 55 kHz → ringdown τ = Q/(πf) ≈ 20 ms, comparable to our 10 ms capture window. So a single capture already **integrates the recent drive history with a causal, decaying weight** — present strong, past fading. That causal asymmetry is precisely a motion blur that _also encodes time-direction_ (it resolves A→B vs B→A, which symmetric blur cannot, because the fading tail points "backward in time"). We do not have to construct the blur in software; the glass's Q-memory is the exposure.

4. **It makes the deck a path-integral deck, literally.** A point-card is a position; a path-segment card is a tiny trajectory. A sum over path-segments **is** a sum over (short) histories — so the in-motion deck is the natural substrate for the interference/path-integral compute we just built on the bench. Points → segments turns "associative recall of states" into "associative recall of _motions_," which is what prediction actually needs.

**Honest status & the experiment it implies (untested hypothesis, strong grounding):**

- We _partially_ did this in [tools/pong_predict_recall.py](tools/pong_predict_recall.py) by adding (vx,vy) as explicit driven axes — but that's the _clumsy_ version (velocity as extra channels). The user's version is more physical and channel-cheap: **let the plate's ringdown carry velocity implicitly** by driving a _moving_ excitation (the ball's last few positions as a brief tone trajectory, or a short chirp) and reading the blurred fingerprint.
- **Buildable test:** enroll cards as short _swept_ drives (position(t−2)→(t−1)→(t) over a few ms) instead of static tones; capture the ring-integrated fingerprint; recall. Compare future-prediction accuracy vs the static-snapshot deck. Prediction: in-motion cards give a _narrower, more accurate_ future because each fingerprint already encodes heading.
- **Honest caveat:** this needs the capture to span the ringdown (it does, ~10 ms vs τ~20 ms) and a drive that actually moves within one capture (a chirp/sweep — the firmware `SWEEP:` command or a fast sequence of `F:`+`PHASE:` updates). Untested; the Q-memory magnitude is favorable but the SNR of the blurred (spread) fingerprint vs a clean static tone is the open question.

**Status:** pinned as a design principle. _Cards should be motions, not positions; the glass's ringdown is the motion-blur exposure; the in-motion deck is a deck of path-segments = the natural substrate for the interference/path-integral compute._ Next experiment candidate once the phase thread is parked.
